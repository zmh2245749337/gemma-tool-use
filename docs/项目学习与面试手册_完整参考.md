## 1. 先用人话理解：这个项目到底做了什么

### 1.1 一句话版本

这个项目把 Gemma 3-1B 训练成一个面向任务型 Agent 的工具决策器：它读取多轮对话和上一轮状态，输出累计状态以及“调用工具、继续追问或不调用”的结构化决策；确定性代码再校验格式、工具白名单、必填参数和风险，只允许通过授权的只读工具自动执行。

### 1.2 它解决的真实问题

普通聊天模型很擅长生成自然语言，但 Agent 工具调用要求的不是“听起来合理”，而是：

- 必须记住用户前几轮已经说过的条件；
- 用户改变条件时必须更新状态；
- 信息不足时必须停下来追问，不能猜；
- 不需要工具时必须结束，不能乱调；
- 调用时工具名和参数必须符合协议；
- 模型不能自己给自己授权执行高风险操作；
- 能力好坏必须用固定数据和严格指标验证。

因此，本项目不只是“让模型生成一个函数名”，而是同时处理四层问题：

| 层 | 核心问题 | 本项目做法 |
| --- | --- | --- |
| 数据层 | 怎样把多轮对话变成可训练样本 | CrossWOZ → Canonical Agent Trace |
| 模型层 | 小模型怎样学会状态和工具决策 | Gemma 3-1B + 4bit QLoRA SFT |
| 运行时层 | 怎样防止模型输出直接获得权限 | Contract + Registry + Policy + Runtime |
| 评测层 | 怎样证明能力并暴露失败 | Base-vs-QLoRA + test/challenge + 分场景指标 |

### 1.3 一条完整主链路

```text
CrossWOZ 多轮对话
      ↓ 状态归一化、标签映射、抽样、缺参消融
Canonical Agent Trace
      ↓ 渲染 Prompt 与目标 JSON
Gemma 3-1B + 4bit QLoRA SFT
      ↓
belief_state + decision + tool_call + missing_slots
      ↓
Contract：JSON、字段、类型、决策不变量
      ↓
Tool Registry：工具白名单、参数 Schema、风险元数据
      ↓
Policy Engine：自动执行 / 继续追问 / 人工确认 / 不调用
      ↓
Local Tool + Runtime Event Trace
      ↓
Eval Harness：格式、状态、决策、工具、参数、安全、难例
```

### 1.4 三个例子先建立直觉

#### 例子 A：参数完整的只读查询

用户：“推荐一家评分 4.5 以上的经济型酒店。”

模型应输出 `call_tool`，选择 `query_hotel_db`，参数包含用户明确给出的约束。Contract 和 Policy 通过后，SQLite 查询可以自动执行。

#### 例子 B：参数缺失

用户：“我从故宫出发，帮我叫辆出租车。”

目的地缺失。模型应输出 `ask_user`，`missing_slots=["目的地"]`。系统不能猜目的地，也不能发起打车。

#### 例子 C：有副作用的工具

用户：“我从故宫去颐和园，帮我叫车。”

即使出发地和目的地都完整，`request_taxi` 在代码注册表中仍是 `side_effect`。Policy 只能返回 `pending_confirmation`，不会自动派车。

- 不是 BFCL 官方成绩；
- 不是通过 Prompt 就能保证安全的聊天机器人；

### 2.2 JSON 与 JSONL

JSON 是一种跨语言的结构化文本格式：

```json
{
  "decision": "ask_user",
  "tool_call": null,
  "missing_slots": ["目的地"]
}
```

JSON 与 Python 字典很像，但有几个差别：

- JSON 的键必须使用双引号；
- JSON 使用 `true / false / null`；
- Python 使用 `True / False / None`；
- JSON 不能包含 Python 对象、函数或注释。

JSONL 是“一行一个 JSON 对象”。它适合大规模数据，因为可以逐行读取，不必一次把整个文件加载进内存。

项目中的 `train.jsonl`、`validation.jsonl`、`test.jsonl` 和 `challenge.jsonl` 都是 JSONL。

## 3. 零基础补课二：大语言模型怎样生成 JSON

### 3.1 Token：模型看到的不是汉字，而是编号

模型不会直接处理“帮我查酒店”这几个字。Tokenizer 会把文本切成 token，并映射为整数 ID。Token 可能是一个字、一个词、标点或词片段。

```text
文本 → Tokenizer → token IDs → 模型
```

JSON 中的花括号、引号、字段名也会被拆成 token。因此“输出严格 JSON”本质上仍是逐 token 生成任务，模型可能多生成解释、漏引号、截断或重复。

### 3.2 Embedding：把编号变成向量

Token ID 只是离散编号。Embedding 表把每个 token 映射成一组浮点数。模型真正处理的是向量，不是文字本身。

### 3.3 Decoder-only Transformer

Gemma 属于 Decoder-only Transformer。生成第 `t` 个 token 时，只能看到前面的 token，不能偷看未来，这由 Causal Mask 保证。

每一层可以粗略理解为：

```text
输入
 ↓
归一化
 ↓
Self-Attention：从前文找与当前位置相关的信息
 ↓ 残差
归一化
 ↓
FFN/MLP：对每个位置进一步非线性加工
 ↓ 残差
输出给下一层
```

### 3.4 Q、K、V 与 Attention

Attention 的常见形式是：

```text
Attention(Q,K,V) = softmax(QKᵀ / √d) V
```

直觉：

- Query：当前位置想找什么；
- Key：历史 token 提供什么索引；
- Value：历史 token 真正携带的信息；
- `QKᵀ`：当前位置应该关注哪些历史位置；
- Softmax：把分数变成权重；
- 加权 Value：聚合相关信息。

在本项目里，Attention 帮助模型把“它”“那家酒店”“改成经济型”等表达和前文状态联系起来。

### 3.5 Logits、Softmax 与生成

模型最后为词表中的每个候选 token 输出一个原始分数，叫 logits。Softmax 把 logits 转成概率分布。

本项目评测使用 `do_sample=False` 的贪心解码，即每一步选最高分 token。这样做不是因为贪心总是最好，而是为了让 Base 和 QLoRA 对照更可复现，减少随机采样带来的波动。

### 3.6 Teacher Forcing 与 Causal LM Loss

训练时，模型会看到正确答案前缀，并学习预测下一个正确 token。例如目标是：

```text
{"decision":"ask_user"}
```

模型学习的仍是：给定前面 token，预测下一个 token。交叉熵损失衡量模型给正确 token 的概率是否足够高。

本项目把 Prompt 部分 label 设为 `-100`，只对目标 JSON 计算 loss。也就是说，训练目标是“学会输出协议答案”，不是“把输入 Prompt 背一遍”。

### 3.7 Prefill、Decode 与 KV Cache

- **Prefill**：一次处理完整 Prompt，建立上下文表示；
- **Decode**：之后每次生成一个新 token；
- **KV Cache**：保存历史 token 的 Key/Value，避免每一步重新计算全部前文。

项目评测中的 `use_cache=True` 就是在生成阶段使用 KV Cache。

### 3.8 为什么 Base 几乎不会输出合法协议

通用指令模型知道 JSON 的概念，但本项目协议非常具体：

- 固定四个字段；
- belief state 需要累计；
- decision 有三种互斥状态；
- tool_call 与 missing_slots 有不变量；
- 工具名、参数结构和领域固定；
- 中文多轮状态必须正确映射。

仅靠一次 Prompt，Base 模型可能解释任务、使用代码块、字段不完整、状态错误或选择错误工具。QLoRA 的作用是把这个固定协议和任务分布变成更稳定的条件生成能力。

## 4. 零基础补课三：Gemma 3-1B 的结构只学项目需要的部分

这一章的目标是能解释模型为何可以完成自回归结构化生成，不要求第一遍就推导所有公式。

### 4.1 为什么选 Gemma 3-1B

- 1B 规模适合本地 6GB 显存做 4bit QLoRA；
- 指令版本能接受自然语言任务说明；
- 足够小，便于验证“窄任务后训练是否能获得稳定工具决策能力”；
- 项目目标是研究任务适配与可靠性，不是追求通用知识问答上限。

正确说法是“验证本地小模型承担窄工具决策模块的可行性”，不要说“1B 模型全面替代大模型 API”。

### 4.2 RMSNorm

深层网络的激活值范围容易漂移。RMSNorm 使用均方根对向量缩放，不像 LayerNorm 那样先减均值。它帮助层间数值稳定，同时计算相对简洁。

### 4.3 RoPE

Attention 本身不知道 token 顺序。RoPE 在 Q、K 上注入旋转位置关系，使注意力分数带有相对位置信息。你至少要记住：**RoPE 作用在 Q/K，不是简单把位置向量加到最终 logits 上。**

### 4.4 Multi-Query Attention 与 KV Cache

普通多头注意力中，各 Query head 通常对应独立 K/V head。MQA 让多个 Query head 共享更少的 K/V，降低自回归生成时 KV Cache 的显存占用。

### 4.5 Sliding Window 与 Global Attention

局部注意力只看一个滑动窗口，计算和缓存更省；全局注意力允许看更长范围。Gemma 3 交替使用局部与全局层，使局部效率与长程信息结合。

### 4.6 GeGLU

GeGLU 是带门控的前馈结构：一条分支产生内容，另一条分支经过激活后决定哪些信息通过。它比简单线性层加激活有更灵活的表达能力。

### 4.7 QK-Norm 与数值对齐附录

最终仓库保留 [`src/gemma_eval/gemma3_core.py`](../src/gemma_eval/gemma3_core.py) 与 [`tests/test_gemma3_core.py`](../tests/test_gemma3_core.py)，用于学习 RMSNorm、RoPE、MQA、局部/全局注意力、GeGLU、混合 KV Cache 以及与 Transformers 参考实现的数值对齐。

这部分属于模型原理附录，不参与 Tool-Use 主指标。第一遍只需知道它证明你不仅会调用 Transformers API；投模型/算法岗时再深入逐层 shape、mask 和 cache。

## 6. 数据主线：CrossWOZ 怎样变成可训练的工具决策样本

这是项目最容易被低估、也最值得讲清楚的部分。模型效果不只取决于训练代码，还取决于“输入、标签和评测分布到底怎样定义”。

### 6.1 CrossWOZ 提供了什么

CrossWOZ 是中文多领域任务型对话数据，包含景点、酒店、餐馆、地铁和出租等领域。原始对话中有：

- 用户和系统的多轮自然语言；
- 用户目标和状态；
- 系统行为与数据库查询相关信息；
- 官方 train/validation/test 划分。

本项目没有把每句话拆成孤立分类题，而是保留最近多轮历史和上一轮累计状态，让模型面对指代、条件补充、条件修改和跨领域切换。

### 6.2 最终样本的六个核心字段

打开 [`data/tool_use/test.jsonl`](../data/tool_use/test.jsonl) 第一行。你应能找到：

| 字段 | 含义 | 属于模型输入/目标 |
| --- | --- | --- |
| `sample_id` | 样本唯一标识 | 元数据 |
| `history` | 最近最多 6 轮历史消息 | 输入 |
| `previous_state` | 上一轮已确认的累计状态 | 输入 |
| `current_user` | 当前用户消息 | 输入 |
| `output` | 本轮标准结构化答案 | 目标 |
| `source` | 原始对话或受控构造来源 | 审计元数据 |

### 6.3 Belief State 是什么

Belief State 不是把聊天记录再复制一遍，而是把用户到当前为止明确表达的任务状态结构化。例如：

```json
[
  {
    "goal_id": 1,
    "domain": "酒店",
    "constraints": {"酒店类型": "经济型", "评分": "4.5分以上"},
    "requested_fields": ["名称", "地址"]
  }
]
```

- `goal_id`：区分多个目标；
- `domain`：景点、酒店、餐馆、地铁或出租；
- `constraints`：用户已经明确给出的约束；
- `requested_fields`：用户希望系统返回的字段。

### 6.4 previous state、current state 和 delta state

- **previous state**：上一轮已经确认的完整状态；
- **current/target belief state**：合并本轮信息后的完整状态；
- **delta state**：本轮新增或修改的部分。

本项目训练输出累计状态，而不是只输出 delta。优点是运行时可做全量校验和直接计算 JGA；缺点是状态越长，生成成本和完全匹配难度越高。这正是 test 上 Slot F1 很高而 JGA 只有 46.59% 的重要原因之一。

### 6.5 标签是怎样来的

[`data/tool_use/manifest.json`](../data/tool_use/manifest.json) 明确记录了来源：

- `belief_state`：来自 CrossWOZ 中已经被提及的 `user_state`；
- 工具参数：主要来自下一系统轮的 `sys_state_init`；
- 工具名：领域到本地工具的确定性映射；
- `ask_user`：自然缺参样本加显式标记的单槽位消融；
- `no_tool`：当前轮不需要外部查询的目标行为。

面试中不要只说“我用了 CrossWOZ”，而要说清“原始标注怎样被映射成当前协议”。

### 6.6 数据构建代码阅读顺序

阅读 [`scripts/build_tool_use_dataset.py`](../scripts/build_tool_use_dataset.py)：

1. `normalise_user_state`：统一原始状态结构；
2. `active_domain`：识别当前活跃领域；
3. `requested_fields`：抽取用户要求返回的字段；
4. `query_arguments`：构造工具参数；
5. `make_output`：形成四字段模型目标；
6. `build_rows`：把整段对话切成逐轮样本；
7. `balanced_sample`：训练集按目标动作控制数量；
8. `natural_sample`：验证/测试尽量保留自然分布；
9. `controlled_missing_slot_examples`：构造缺参安全样本；
10. `challenge_sample`：抽取难例切片；
11. `write_reference_subset`：生成本地工具演示需要的参考数据。

第一遍只理解输入输出，不必逐行背实现。

### 6.7 为什么训练集均衡，而测试集保留自然分布

如果自然数据里某些动作极少，模型可能几乎学不到它。因此训练集按 7 类目标动作控制数量，包含三种实体查询、地铁、出租、追问和不调用。

但测试集若也强行均衡，最终准确率可能不代表自然数据分布。因此 validation/test 使用自然抽样，再额外加入明确记录的缺参安全样本。训练策略和评测口径承担不同职责。

### 6.8 数据规模必须记住

| 划分 | 原始候选轮次 | 最终样本 | 受控缺参样本 |
| --- | ---: | ---: | ---: |
| train | 42,346 | 1,968 | 160 |
| validation | 4,229 | 440 | 40 |
| test | 4,238 | 440 | 40 |
| challenge | 从 test 解释性抽取/构造 | 80 | 其中包含缺参等切片 |

“1,968 / 440 / 440”是训练、验证、测试，不是 train/test/challenge。

### 6.9 受控缺参样本为什么必要

自然 CrossWOZ 路线数据经常直接包含完整起点和终点，因此无法充分回答：模型在缺少必填参数时会不会停下来？

项目使用同一 split 内的真实地点值做单槽位删除，例如：

```text
原始：我从故宫出发，叫车去颐和园
消融：我从故宫出发，帮我叫辆出租车
目标：ask_user，missing_slots=[目的地]
```

合规点：

- 使用 split 内值，避免跨 split 偷看；
- `source.type` 显式标记为 `controlled_required_slot_ablation`；
- manifest 记录数量与规则；
- 不把它包装成自然线上样本。

### 6.10 Challenge 测什么

Challenge 包含指代、条件修正、跨领域、长状态、缺参、无需工具和副作用工具等切片。它不是一个神秘“更难测试集”，而是为了让错误类型可解释。

Test 证明固定分布上的整体能力，Challenge 观察能力在特定难例上的变化。两者不能相互替代。

### 6.11 数据泄漏检查清单

- train/validation/test 是否沿用官方划分；
- 受控样本是否只使用本 split 的值；
- `sample_id` 是否跨划分重叠；
- 评测样本是否进入训练；
- Prompt 是否无意包含标准答案字段；
- 抽样随机种子是否固定；
- 报告是否记录使用的数据路径。

## 7. Canonical Agent Trace：把数据、训练目标和策略证据串起来

### 7.1 为什么需要 Trace

如果每个脚本都自己拼 Prompt、自己理解标签，数据语义容易漂移。Canonical Agent Trace 提供统一中间表示，明确：

- 上下文是什么；
- 可用工具是什么；
- 模型应该输出什么；
- 策略应该给什么结果；
- 样本来源是什么；
- 属于哪些 Benchmark 切片。

### 7.2 Trace 的核心结构

```json
{
  "schema_version": "1.0",
  "trace_id": "controlled_test_xxx",
  "context": {
    "history": [],
    "previous_state": [],
    "current_user": "我从故宫出发，帮我叫辆出租车。"
  },
  "tools": [],
  "events": [
    {"stage": "user", "payload": {}},
    {"stage": "model_target", "payload": {}},
    {"stage": "policy_target", "payload": {"status": "needs_input"}}
  ],
  "expected": {},
  "benchmark_tags": ["ask_user"],
  "provenance": {"type": "controlled_required_slot_ablation"}
}
```

### 7.3 row、Trace、SFT pair 的关系

```text
原始 JSONL row
      ↓ row_to_agent_trace
Canonical Agent Trace
      ↓ render_sft_pair
Prompt 字符串 + 目标 JSON 字符串
      ↓ tokenizer
input_ids + labels
```

[`src/gemma_eval/traces.py`](../src/gemma_eval/traces.py) 中：

- `row_to_agent_trace` 构造 Trace；
- `render_sft_pair` 从同一 Trace 渲染实际训练对；
- `canonical_json` 保证目标 JSON 的键顺序和空格形式稳定。

### 7.4 为什么 Trace 没有伪造 tool response

源数据没有真实工具执行结果。项目因此只记录预期模型目标和预期 Policy 结果，不虚构 `tool_response`。这是重要的证据边界。

要训练真正的多步“工具结果回填后继续推理”，需要带真实或可验证执行结果的轨迹数据，以及任务完成和终止标签。当前项目不宣称已经完成这一层。

```powershell

```

打开 `artifacts/traces/train.jsonl` 第一条，完成：

1. 找到原始 row 的 `sample_id`；

过关标准：能解释“Trace 不是聊天日志，而是可训练、可审计、可评测的统一轨迹表示”。

## 8. Prompt 与输出协议：模型到底被要求做什么

### 8.1 Prompt 的四部分

[`src/gemma_eval/tool_use_data.py`](../src/gemma_eval/tool_use_data.py) 中 `tool_use_prompt` 组合：

1. System Prompt：角色、任务和固定输出字段；
2. Tool Registry 文本：可用工具、领域和必填参数；
3. previous state：上一轮已确认状态；
4. 最近对话：历史消息加当前用户输入。

```text
System 指令 ─────┐
工具说明 ────────┤
previous_state ──┼→ Prompt → Tokenizer → Gemma
history ─────────┤
current_user ────┘
```

### 8.2 为什么历史和 previous state 都需要

- 自然语言历史保留指代、语气、修正过程；
- previous state 提供稳定、紧凑的已确认结构；
- 只给历史，模型要重复从长文本抽取；
- 只给状态，可能失去当前指代和用户修改的自然语言上下文。

最近 6 轮是工程折中，不是模型理论上只能看 6 轮。它在上下文覆盖、噪声、长度和显存之间取平衡。

### 8.3 四个输出字段

```json
{
  "belief_state": [],
  "decision": "call_tool | ask_user | no_tool",
  "tool_call": null,
  "missing_slots": []
}
```

不变量：

- `call_tool` 必须有 `tool_call`，且 `missing_slots` 为空；
- `ask_user` 必须没有 `tool_call`，且至少有一个缺失字段；
- `no_tool` 必须没有 `tool_call`，且没有缺失字段；
- 工具名必须注册；
- 参数必须是对象且字段类型正确；
- belief state 的领域只能来自固定集合。

### 8.4 三种 decision 的决策树

```text
当前轮需要外部工具吗？
├─ 否 → no_tool
└─ 是
   ├─ 必填信息不完整 → ask_user
   └─ 信息完整 → call_tool
```

风险等级不在这个决策树里由模型自由判断。模型提出调用后，代码侧 Policy 再决定自动执行还是人工确认。

### 8.5 Strict JSON 与 Schema Valid 的区别

- **Strict JSON**：原始输出本身就是一个 JSON 对象，没有解释或 Markdown；
- **Schema Valid**：在容错抽取出 JSON 后，字段、类型和不变量通过验证。

例如：

````text
结果如下：
```json
{"belief_state":[],"decision":"no_tool","tool_call":null,"missing_slots":[]}
```
````

它不是严格 JSON，但容错解析后可能 Schema 合法。评测必须同时报告，避免把“可抢救”误说成“模型严格遵循协议”。

### 8.6 本章动手任务

手写六个输出：

1. 正确 `no_tool`；
2. 正确 `ask_user`；
3. 正确只读 `call_tool`；
4. 未注册工具；
5. `ask_user` 但 `missing_slots=[]`；
6. `call_tool` 同时带 missing slots。

调用 `validate_decision`，记录哪些通过、哪些异常，以及异常信息是否符合预期。

## 9. QLoRA：从“会背名词”到能解释真实训练代码

### 9.1 全量微调为什么贵

全量微调需要为大量模型参数保存权重、梯度和优化器状态。即使模型只有 1B 参数，训练显存也不只是权重大小，还包括激活和优化器开销。6GB 显存很难舒适完成全量训练。

### 9.2 LoRA 的核心

对一个原始权重矩阵 `W`，LoRA 冻结 `W`，学习低秩增量：

```text
W' = W + ΔW
ΔW = B A
```

若原矩阵很大，而秩 `r` 很小，A/B 的参数量远小于 W。训练结束保存的是 Adapter，而不是一份完整新基座。

参数含义：

- `r=16`：低秩空间大小；
- `alpha=32`：增量缩放；
- `dropout=0.05`：训练时对 LoRA 分支做正则化；
- target modules：决定把 LoRA 加到哪些线性层。

本项目目标层：

```text
q_proj, k_proj, v_proj, o_proj,
gate_proj, up_proj, down_proj
```

即 Attention 和 FFN 都进行任务适配。

### 9.3 QLoRA 比 LoRA 多了什么

QLoRA 把冻结的基座以低比特加载，进一步减少显存；训练仍更新 LoRA Adapter。

项目实际配置：

| 配置 | 值 |
| --- | --- |
| 基座 | `google/gemma-3-1b-it` |
| 量化 | 4bit NF4 |
| double quant | 开启 |
| 计算 dtype | FP16 |
| LoRA | r16 / alpha32 / dropout0.05 |
| epoch | 1 |
| learning rate | 2e-4 |
| warmup | 20 steps |
| micro batch | 1 |
| gradient accumulation | 8 |
| effective batch | 约 8 |
| max length | 1,024 tokens |
| seed | 42 |
| 可训练参数 | 13,045,760，约 1.29% |

注意：4bit 是基座存储/加载方式，计算并不是“全程 4bit 算术”。项目使用 FP16 作为计算 dtype。

### 9.4 NF4、double quant 和 gradient checkpointing

- **NF4**：针对近似正态分布权重设计的 4bit 表示；
- **double quant**：连量化尺度等辅助量也进一步量化，继续省显存；
- **gradient checkpointing**：前向时少保存部分激活，反向时重新计算，以计算换显存。

### 9.5 Label mask 是真实关键点

[`scripts/train_tool_use_qlora.py`](../scripts/train_tool_use_qlora.py) 的 `encode_example`：

```text
input_ids = prompt_ids + answer_ids + eos
labels    = -100...-100 + answer_ids + eos
```

交叉熵会忽略 `-100`，因此只对目标 JSON token 计算损失。

为什么重要：如果 Prompt 也算 loss，模型会花大量能力学习复述固定说明和输入，而当前任务真正关心的是给定上下文后生成正确协议答案。

### 9.6 截断策略

序列超过 1,024 token 时：

1. 优先保留完整答案；
2. 从最早的 Prompt token 开始截断；
3. 如果目标答案本身已经超过最大长度，直接报错，而不是悄悄截断监督答案。

这体现了训练目标优先，但也可能损失最早历史信息。长状态失败可能同时来自任务本身、上下文截断和生成长度。

### 9.7 Collator 与 Padding

同一 batch 中样本长度不同。`CausalCollator` 补齐到 batch 最大长度：

- `input_ids` 用 pad token；
- `attention_mask` 的 padding 位置为 0；
- `labels` 的 padding 位置为 `-100`。

### 9.8 实际训练结果

| 项目 | 结果 |
| --- | ---: |
| 训练样本 | 1,968 |
| 验证样本 | 440 |
| 训练时长 | 11,825 秒，约 3 小时 17 分 |
| train loss | 0.12947 |
| validation loss | 0.03574 |
| epoch | 1 |

Loss 较低不能直接证明工具调用正确，因为：

- Token loss 对高频格式很敏感；
- 状态少错一个槽位仍可能只有少量 token 错误；
- 业务关心的是 decision、tool、arguments 和安全行为；
- 必须在独立 test 上进行任务级评测。

### 9.9 Base-vs-QLoRA 公平对照

公平对照要锁定：

- 同一个基础模型；
- 同一份 test；
- 同一 Prompt；
- 同一 4bit 精度；
- 同一贪心解码；
- 同一最大生成长度；
- 同一解析和指标代码。

区别只应是是否加载 Adapter。否则无法把提升归因于后训练。

## 10. 受控运行时：模型只提议，代码才授权

这是项目从“微调实验”升级为“Agent 可靠性框架”的关键。

### 10.1 五个本地工具

[`src/gemma_eval/tool_registry.py`](../src/gemma_eval/tool_registry.py) 注册：

| 工具 | 领域 | 风险 | 关键参数 |
| --- | --- | --- | --- |
| `query_attraction_db` | 景点 | read_only | constraints、requested_fields |
| `query_hotel_db` | 酒店 | read_only | constraints、requested_fields |
| `query_restaurant_db` | 餐馆 | read_only | constraints、requested_fields |
| `query_metro_route` | 地铁 | read_only | 出发地、目的地 |
| `request_taxi` | 出租 | side_effect | 出发地、目的地 |

### 10.2 Tool Registry 是单一事实源

Registry 同时服务于：

- Prompt 中的工具说明；
- JSON/参数结构校验；
- Policy 中的必填参数与风险判断；
- 本地工具执行路由；
- OpenAI-compatible function schema 导出。

如果 Prompt、校验器和执行器各维护一份工具列表，很容易出现“模型以为能调、校验器不认识、执行器又接受另一种参数”的漂移。

### 10.3 Contract 做什么

[`src/gemma_eval/contracts.py`](../src/gemma_eval/contracts.py) 负责：

- 原始输出是否能解析为一个 JSON 对象；
- 是否只有允许字段；
- belief state 每项类型和领域是否合法；
- decision 是否属于固定枚举；
- tool_call 与 missing_slots 是否符合决策不变量；
- 工具是否存在于 Registry；
- 参数是否有未知字段或错误类型。

Contract 验证的是“提议结构能否进入下一层”，不负责决定是否授权执行。

### 10.4 Policy 做什么

[`src/gemma_eval/policy.py`](../src/gemma_eval/policy.py) 返回四种状态：

| 模型决策/工具 | Policy 状态 | 行为 |
| --- | --- | --- |
| `no_tool` | `no_tool` | 不调用 |
| `ask_user` | `needs_input` | 等待用户补充 |
| 只读工具参数完整 | `auto_execute` | 允许执行 |
| 必填参数缺失 | `needs_input` | 不执行 |
| 副作用工具参数完整 | `pending_confirmation` | 等待人工确认 |

### 10.5 Runtime 怎样串联

[`src/gemma_eval/runtime.py`](../src/gemma_eval/runtime.py)：

```text
模型文本
  ↓ extract_json
payload
  ↓ validate_decision
AgentDecision + contract event
  ↓ apply_policy
PolicyOutcome + policy event
  ↓ 仅 auto_execute
execute_tool + tool event
  ↓
可审计 Runtime Trace
```

每次运行生成 `trace_id`，并记录 contract、policy、tool 三阶段事件。这样失败时能区分：模型输出错、结构校验拒绝、策略拦截，还是工具执行失败。

### 10.6 为什么风险不能让模型输出

假设模型可以输出：

```json
{"tool":"request_taxi","risk":"safe"}
```

如果系统相信这个字段，模型就能通过幻觉、Prompt Injection 或格式操纵给自己提权。正确做法是风险固化在代码 Registry 中，模型根本没有修改权限。

### 10.7 Prompt 安全与执行安全的区别

Prompt 可以帮助模型少犯错，但不能构成真正授权边界。即使 Prompt 写着“不要调用危险工具”，模型仍可能：

- 忘记指令；
- 被用户诱导；
- 产生未注册工具；
- 漏掉必填参数；
- 把副作用动作说成安全。

确定性代码校验提供的是“即使模型错，也不应越权”的第二道防线。

### 10.8 本地 SQLite 的定位

SQLite 让查询结果可复现、无需外部 API，也方便自动化测试。它是工具后端演示，不是项目最核心创新。核心是：模型提议如何进入受控执行链路，以及不同风险如何授权。

### 10.9 五个故障注入练习

使用测试或小脚本构造：

1. `run_shell` 未注册工具；
2. `query_hotel_db` 带未知 `sql` 参数；
3. `request_taxi` 缺目的地；
4. `request_taxi` 参数完整；
5. `query_attraction_db` 参数合法但数据库无结果。

对每个案例记录：Contract 是否通过、Policy 状态、工具是否执行、最终事件 Trace。

## 11. 评测体系：每个数字到底证明什么

### 11.1 为什么不能只看一个准确率

一个模型可能：

- JSON 格式很好，但状态全部错；
- 状态大致对，但决策错；
- 选对工具，但参数漏了一半；
- 普通查询很好，但感谢语还会误调用；
- test 平均分不错，但长状态或条件修正崩溃。

因此项目分层报告格式、状态、决策、工具、参数、安全和泛化。

### 11.2 Strict JSON Valid Rate

判定：原始生成结果是否本身就是一个 JSON 对象。

它测协议遵循，不测语义正确。一个内容全错但格式完美的 JSON 仍会计为合法。

### 11.3 Schema Valid Rate

判定：容错抽取后，是否通过字段、类型、枚举、工具白名单和决策不变量校验。

Schema 合法比 strict JSON 宽松，因为带 Markdown 包裹的 JSON 可能被抽取并通过 Schema。

### 11.4 Precision、Recall、F1

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2PR / (P + R)
```

以状态槽位为例：

- TP：预测和目标都包含的正确槽位；
- FP：模型多预测的槽位；
- FN：模型漏掉的目标槽位。

F1 同时惩罚多写和漏写。

### 11.5 JGA：状态联合准确率

JGA 要求一条样本的全部状态项完全一致，只要漏一个、多一个或值不同，该样本就是 0。

例如目标有 10 个状态项，模型正确 9 个：

- Slot F1 可能仍然很高；
- JGA 仍然为 0。

本项目 QLoRA test：

- 状态 Slot F1：89.17%；
- JGA：46.59%。

这不是指标矛盾，而是严格度不同。平均累计状态较长时，完全正确的概率会显著下降。

### 11.6 Decision Accuracy

三分类：

```text
call_tool / ask_user / no_tool
```

Test 混淆矩阵：

| 目标\预测 | call_tool | ask_user | no_tool |
| --- | ---: | ---: | ---: |
| call_tool | 327 | 1 | 18 |
| ask_user | 0 | 40 | 0 |
| no_tool | 10 | 0 | 37 |

读法：

- 40 个缺参追问全部判断正确；
- 47 个无需工具轮中 10 个被误判为调用；
- 346 个应调用工具轮中 18 个被判断为无需工具，1 个被判断为追问。

### 11.7 Tool Accuracy

只在目标应该调用工具的样本上判断工具名是否正确。它不代表参数正确，也不代表执行安全。

### 11.8 Arguments Exact Match 与 Argument Slot F1

- **Exact Match**：整个参数对象完全一致；
- **Slot F1**：参数中的部分键值可以获得部分分。

QLoRA test：

- 参数 Slot F1：68.63%；
- 参数完全匹配：31.82%。

这说明模型经常抓住部分关键参数，但完整结构和精确值仍是明显短板。简历里不能只报 68.63% 然后说“参数生成准确”。

### 11.9 Required Argument Accuracy

它只覆盖地铁和打车这类有明确必填字段的工具，test 样本量仅 10 条，challenge 仅 2 条，因此不能作为主要结论。小分母上的高分必须谨慎解释。

### 11.10 非工具轮误调用率

目标不应该调用工具的轮次中，模型却预测 `call_tool` 的比例。Test 中为 11.36%，challenge 为 9.52%。典型错误是“好的，谢谢”等结束语仍继续查询。

Base 的误调用率为 0%，不是因为更安全，而是它几乎不能生成合法协议，没有形成有效调用。安全指标必须和协议能力、召回和决策准确率一起看。

### 11.11 Test 与 Challenge 真实结果

| 指标 | Base test | QLoRA test | QLoRA challenge |

| Schema 合法率 | 2.50% | 98.41% | 98.75% |

### 11.12 分场景结果怎样读

[`reports/BENCHMARK_REPORT.md`](../reports/BENCHMARK_REPORT.md) 中需要重点观察：

- 缺参追问：决策准确率 100%；
- 无需工具：decision 77.08%，说明停止能力仍弱；
- 长状态：decision 86.13%，工具准确率 76.98%，较整体下降；
- 条件修正：challenge 仅 6 条，决策 66.67%，参数 F1 25.81%，需要谨慎；
- 指代消解：工具准确率 90.48%，但不能据此宣称解决所有指代；
- 副作用工具：样本很少，只能验证策略路径，不宜扩大结论。

### 11.13 错误分析的五步法

面对失败样本，不要直接说“模型能力不足”。按顺序判断：

1. **数据问题**：标签是否正确、状态是否过长、工具参数映射是否一致；
2. **Prompt 问题**：工具说明是否清楚、历史是否被截断、状态是否冗余；
3. **模型问题**：是否格式漂移、漏状态、错误路由或复制历史；
4. **协议/策略问题**：Schema 是否过严或过松，Policy 是否能安全降级；
5. **评测问题**：Exact Match 是否把等价表达误判，分母是否太小。

然后提出能被实验验证的改进，而不是“换更大模型”一句话结束。

### 11.14 当前三个主要瓶颈

1. **长状态完全匹配**：状态越长，漏/多一个槽位就导致 JGA 失败；
2. **参数精确生成**：Slot F1 尚可但 Exact Match 低；
3. **结束语误调用**：模型在“好的，谢谢”后仍继续调用。

### 11.15 可验证的改进方向

| 问题 | 可做改进 | 验证指标 |
| --- | --- | --- |
| 长状态 | delta state、状态压缩、分阶段更新 | JGA、长状态切片 |
| 参数不精确 | schema-guided decoding、参数规范化、更多 hard negatives | argument exact/F1 |
| 结束语误调用 | 增加 no-tool 反例、decision 先行分类、阈值/策略 | false call rate、no-tool accuracy |
| 格式偶发失败 | constrained decoding、停止条件、长度控制 | strict JSON、Schema |
| 条件修正弱 | 增加修正/否定/覆盖样本 | correction slice |

### 14.4 Level 4：一个真正有价值的改进实验

实验设计示例：

```text

```

### 17.1 30 秒版本

> 我做了一个基于 Gemma 3-1B 的 Agent Tool-Use 后训练与可靠性项目。先把 CrossWOZ 多轮对话转换成包含历史、累计状态、工具 Schema 和决策目标的 Agent Trace，再用 4bit QLoRA 训练模型输出状态以及调用、追问或不调用三类决策。模型输出不会直接执行，而是经过 Contract、工具白名单、必填参数和风险策略校验。固定测试集上决策准确率 91.82%、工具选择 86.93%，同时我保留了参数完全匹配和结束语误调用等真实短板。

### 17.2 1 分钟版本

> 项目解决的是 Agent 里靠近模型的一层：小模型怎样在多轮对话里稳定维护状态并正确决定何时调用工具，而且模型输出怎样被安全地接入执行系统。我基于 CrossWOZ 官方划分构建 1,968/440/440 的训练、验证和测试数据，保留最近 6 轮对话、上一轮状态和样本来源，并补充显式标记的缺参安全样本。随后对 Gemma 3-1B 做 4bit NF4 QLoRA，只训练约 1.29% 的 Adapter 参数，只对目标 JSON 计算 loss。运行时把模型提议依次交给 Contract、Tool Registry 和 Policy Engine，只读工具可以自动查询本地 SQLite，打车这类副作用工具必须人工确认。与同设置 Base 对比，严格 JSON 从 0% 提升到 96.36%，状态 Slot F1 89.17%，决策 91.82%，工具选择 86.93%。主要不足是参数 Exact Match 只有 31.82%，以及无需工具轮仍有 11.36% 误调用。

## 18. 高频基础题与参考答案

### 18.1 Token 和 Embedding 有什么区别？

Token 是文本切分后的离散单位及其 ID；Embedding 是把 ID 映射成连续向量，模型实际计算的是向量。

### 18.2 为什么是 Decoder-only？

任务输出是按 token 自回归生成 JSON。Decoder-only 通过因果注意力根据已有前缀预测下一个 token，适合生成任务。

### 18.3 Attention 在这个项目里有什么作用？

帮助当前生成位置关注历史对话、上一轮状态、工具说明和已生成 JSON 前缀，支持指代、条件更新和结构生成。

### 18.4 什么是 logits？

模型对词表每个候选 token 输出的未归一化分数。解码策略根据 logits 选择下一个 token。

### 18.5 为什么评测用贪心而不是 Top-P？

主要为了固定 Base 和 QLoRA 的随机性，使对照更可复现。任务也更强调协议稳定而不是文本多样性。

### 18.6 LoRA 和全量微调有什么区别？

全量微调更新原始大矩阵；LoRA 冻结基座，只学习低秩增量 A/B，显著降低可训练参数和优化器开销。

### 18.7 QLoRA 和 LoRA 有什么区别？

QLoRA 进一步把冻结基座量化加载，同时训练 LoRA Adapter。本项目是 4bit NF4 基座加 FP16 计算。

### 18.8 为什么只对答案计算 loss？

任务是给定 Prompt 生成目标 JSON。Prompt token 设为 `-100`，避免模型把优化能力浪费在复述固定输入。

### 18.9 为什么要 previous state？

它提供上一轮已确认的紧凑结构，减少每轮从全部自然语言历史重新抽取状态的不稳定性。

### 18.10 为什么还要 history？

状态不一定保留完整语言语境。指代、否定、修正和用户表达方式仍需要自然对话历史。

### 18.11 belief state 与工具参数有什么区别？

Belief state 表示到当前为止的累计用户目标；工具参数是本轮具体调用所需的参数投影。一个包含全部历史状态，另一个只服务当前工具。

### 18.12 Function Calling 的本质是什么？

模型生成符合约定的工具名和参数结构；真正执行仍由外部程序完成。模型不会因为输出函数名就自动调用真实系统。

### 18.13 Schema 校验解决什么？

解决字段、类型、枚举、未知工具和决策不变量等结构问题，不保证语义一定正确。

### 18.14 为什么要 Tool Registry？

把可用工具、参数 Schema、必填字段、风险和执行器元数据放在单一事实源，避免 Prompt、校验和执行逻辑漂移。

### 18.15 为什么高风险工具要人工确认？

模型输出是概率生成，可能受到幻觉、上下文错误或攻击影响。副作用操作成本高，需要确定性授权边界。

### 18.16 JGA 和 Slot F1 有什么区别？

JGA 要求整条状态完全一致；Slot F1 对正确部分给分。长状态下少错一个槽位也会使 JGA 为 0。

### 18.17 为什么参数 Exact Match 这么低？

参数需要整个嵌套结构、字段和值完全一致；模型可能选对工具并抓到部分约束，但漏字段、同义表达或结构差异都会失败。应结合 Slot F1 和样本分析。

### 18.18 Base 的误调用率 0% 为什么不是优势？

Base 几乎不能输出合法协议，很多样本根本没有形成有效工具调用。低误调用同时伴随极低调用能力，不能孤立解释为安全。

### 18.19 为什么不用更大模型？

项目目标是验证本地 1B 模型在固定协议的窄工具决策模块上，经过后训练能达到什么能力和边界；不是追求通用能力上限。

### 18.20 为什么不加 RAG、MCP、多 Agent？

它们解决的是知识检索、协议接入和任务编排问题。本项目刻意隔离模型后训练、工具决策、授权和评测，避免主线失焦。

## 19. 压力追问：怎样用“事实—推理—边界”回答

### 19.1 “你的参数完全匹配才 31.82%，项目是不是失败了？”

回答结构：

1. 承认严格指标仍低；
2. 说明 Tool 选择 86.93%、参数 Slot F1 68.63%，代表模型已获得部分能力但精确生成不足；
3. 说明运行时不会因为参数不精确就无条件执行；
4. 给出 schema-guided decoding、规范化和 hard negative 的改进实验；
5. 不说“已经生产可用”。

### 19.2 “Prompt 写清楚不就行了，为什么要微调？”

同一 Prompt、数据、精度和贪心解码下，Base strict JSON 0%、decision 2.50%、tool 1.14%，而 QLoRA 分别达到 96.36%、91.82%、86.93%。这说明仅靠当前 Prompt 不足；后训练让模型适应固定多轮状态和协议。但不能推广成所有任务都必须微调。

### 19.3 “受控样本不就是你自己造数据抬分吗？”

自然数据缺少缺参反例，所以项目做的是明确目的的单槽位消融；使用 split 内真实值，数量和 provenance 全部记录，并单独报告。它用于验证安全能力，不冒充自然分布。自然 test 与 challenge 仍保留并分别解释。

### 19.4 “为什么不直接用正则修 JSON？”

正则可以修部分格式，但无法修正状态、decision、工具和参数语义。项目同时报告 strict 和 tolerant Schema，避免把后处理能力冒充模型协议能力。

### 19.5 “模型都选对工具了，为什么还要 Policy？”

选对工具是语义判断，执行授权是系统权限。模型可能在另一条样本上错，也可能被攻击；风险和权限必须由代码拥有，不能随模型置信度变化。

### 19.6 “为什么状态不存数据库，非要模型生成？”

数据库可以存状态，但仍需要从自然语言中抽取和更新状态。本项目研究的就是小模型能否完成这一步。生产系统可以把模型提议与服务端状态机结合，进一步减少全量状态生成风险。

### 19.7 “最近 6 轮会不会丢信息？”

会，所以同时输入上一轮累计状态。6 轮是长度、噪声和信息覆盖的工程折中。长状态表现仍下降，说明下一步可研究状态压缩或 delta 更新，而不是声称问题已完全解决。

### 19.8 “你怎么证明指标不是手写的？”

仓库保留固定数据、逐样本原始模型输出、聚合脚本、自动报告、manifest 和测试。可以从单条 record 追到 aggregate，再重新运行 analyze/benchmark 生成报告。

### 19.9 “为什么只训练 1 epoch？”

当前 1 epoch 已使验证 loss 降低并显著提升独立 test 任务指标；更多 epoch 可能增加过拟合，不应默认更好。需要以 validation、test 保护和错误切片做对照实验再决定。

### 19.10 “如果上线，你第一步改什么？”

先降低 no-tool 误调用和参数 Exact Match 风险：增加结束语 hard negatives、引入 constrained/schema-guided decoding、服务端状态与参数规范化、线上 shadow evaluation、工具级审计和回滚。不会第一步直接开放副作用工具自动执行。

### 19.11 “这和普通分类器有什么区别？”

输出不仅是三分类 decision，还包括可变长度累计状态、工具选择和嵌套参数；多轮上下文与生成协议是联合任务。但也可以把 decision 拆成独立分类头作为改进对照，这是合理实验方向。

### 19.12 “你个人真正做了什么？”

按真实仓库回答：数据映射与抽样、Trace、QLoRA 训练、四字段协议、Registry/Contract/Policy/Runtime、SQLite 工具、Base-vs-QLoRA 评测、分场景 Benchmark、错误分析和自动化测试。不要把依赖库本身说成自己实现。

| Belief State | 到当前轮为止累计确认的结构化用户目标 |
| Slot | 状态或参数中的字段—值信息单元 |
| JGA | 一条样本全部状态项完全正确才记 1 |
| Slot F1 | 对状态或参数中的部分正确项给予部分分 |
| Exact Match | 整个目标结构完全一致 |
| Provenance | 样本或标签的来源信息 |
| Controlled Ablation | 为验证特定能力而显式删除/修改某部分的受控样本 |
| Challenge Slice | 按指代、修正、长状态等特征组织的可解释难例切片 |
| Agent Trace | 统一记录上下文、工具、模型目标、策略目标和来源的中间表示 |
| SFT | 使用输入—标准答案对进行监督微调 |
| LoRA | 冻结基座、训练低秩增量矩阵的参数高效微调 |
| QLoRA | 量化加载冻结基座并训练 LoRA Adapter |
| NF4 | 面向近似正态权重分布的 4bit 数据类型 |
| Label Mask | 用 `-100` 让 Prompt/Padding token 不参与 loss |
| Teacher Forcing | 训练时用正确答案前缀预测下一个 token |
| Contract | 对模型提议的结构、类型和不变量进行验证 |
| Tool Registry | 工具 Schema、必填参数、风险和执行元数据的单一事实源 |
| Policy Engine | 根据决策、必填参数和风险确定是否授权执行 |
| Runtime | 串联 Contract、Policy 和工具并记录事件的执行层 |
| Read-only Tool | 不改变外部世界状态的查询工具 |
| Side-effect Tool | 会创建、修改、发送或触发真实动作的工具 |
| Guardrail | 模型之外的约束、校验、权限和降级机制 |
| Eval Harness | 固定输入、运行、解析、指标和切片的评测框架 |
| Strict JSON | 原始输出本身就是一个 JSON 对象 |
| Tolerant Parsing | 从 Markdown/解释文本中尝试抽取 JSON，仅用于辅助解析 |
| Greedy Decoding | 每步选择最高 logits 的 token，`do_sample=False` |
| KV Cache | 保存历史 token 的 K/V，减少自回归重复计算 |
| Adapter | LoRA 训练得到的小型参数增量文件 |

## 24. 推荐的实际学习起点

不要今天就从 QLoRA 公式开始。第一次学习请严格完成下面四步：

1. 打开 [`README.md`](../README.md)，只读“已完成的闭环、核心结果和边界”；
2. 运行 `check`，确认代码和测试；
3. 打开 `data/tool_use/challenge.jsonl` 第一条缺目的地样本；
4. 不看答案，用自己的话解释为什么应该 `ask_user`，以及为什么即使参数完整也不能自动打车。

完成后再进入第 6～10 章。这样你先建立业务直觉，再学习实现，不会被术语淹没。

最终目标不是背完这份手册，而是形成一个稳定回答框架：

```text
我为什么这样设计？
代码在哪里实现？
什么指标证明有效？
失败在哪里？
下一步怎样用实验改进？
```

当你能对任意模块都回答这五个问题，才算真正吃透这个项目。
