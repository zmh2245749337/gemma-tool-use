## 0. 先学会一种说话方式

这个项目里的每个问题，都按四步回答：

```text
先说遇到了什么问题
→ 再说我具体怎么做
→ 再用代码或指标证明
→ 最后主动说清边界
```

推荐这样开场：

> 我当时主要关注两件事：一是模型在多轮对话里能否保留用户前面说过的条件，二是模型生成工具建议以后，系统如何完成检查和授权。所以我一边用 QLoRA 训练状态和工具决策，一边把真正的执行权限留在代码侧。

先让面试官理解你为什么做，再用技术名词补充实现证据。

## 1. 这个项目到底是什么

### 1.1 自己先这样理解

这个项目聚焦 Agent 的工具决策层：

```text
模型看完多轮对话以后，
能否记住当前状态，
知道什么时候调用工具，
什么时候缺信息要追问，
什么时候应该停止，
以及它的建议怎样被安全地接入执行系统。
```

### 1.2 面试开场可以这样说

> 我这个项目主要解决 Agent 的工具决策问题。普通小模型即使能聊天，在多轮状态维护、调用时机和缺参追问上仍会出现波动。我的做法是先用 CrossWOZ 构造多轮状态和工具决策数据，再用 4bit QLoRA 微调 Gemma 3-1B。模型负责输出状态和工具建议，代码侧负责格式、白名单、必填参数和风险检查，然后决定是否执行。

### 1.3 15 秒版本

> 我用 QLoRA 把 Gemma 3-1B 适配成一个多轮工具决策器，再用确定性代码控制工具执行权限，最后用固定测试集分别评估状态、决策、工具、参数和误调用。

### 1.4 面试官继续问“它和普通 Function Calling 有什么区别”

> 普通演示通常展示模型生成函数名。我这里增加了三层：第一，输入里有多轮历史和上一轮累计状态；第二，模型同时判断调用、追问和结束；第三，模型输出先经过独立策略层授权。实验部分还做了 Base 和 QLoRA 的同口径评测。

### 1.5 项目范围

> 这是一个固定任务协议下的本地后训练和可靠性实验。它验证了多轮状态、工具决策和受控执行链路，当前证据范围覆盖离线测试和本地 Demo。

## 2. 为什么选 Gemma 3-1B

### 2.1 自己先这样理解

项目想验证一个具体问题：

> 一个可以本地训练的小模型，经过针对性后训练后，能否承担 Agent 里范围明确、协议固定的工具决策模块。

### 2.2 面试可以这样说

> 我选 Gemma 3-1B 主要是因为这个项目研究窄任务适配。1B 模型在我的 6GB 显存上可以用 4bit QLoRA 完成本地训练，也方便做 Base 和 Adapter 的严格对照。这样我可以完整研究数据、协议、运行时和评测，同时保留整个训练过程的可复现性。

### 2.3 如果追问“那为什么不用大模型 API”

> 大模型 API 很可能开箱效果更好。我这次选择本地小模型，是为了完整观察工具决策能力如何通过数据和后训练获得，以及能力瓶颈出现在哪里。实验说明固定协议下的本地小模型具有一定可行性，同时参数精确生成仍然是明显短板。

### 2.4 结论范围

> 当前结论适用于固定协议下的本地工具决策任务。项目完成了 Base 与 QLoRA 对照，模型规模之间的横向比较可以作为后续实验。

## 3. 数据从哪里来，怎样整理成训练样本

### 3.1 CrossWOZ 用人话怎么讲

> CrossWOZ 是中文任务型对话数据，里面有景点、酒店、餐馆、地铁和出租等领域。除了聊天文本，它还带有用户状态和系统查询相关标注，所以比较适合把多轮对话转换成状态跟踪和工具决策任务。

### 3.2 一条数据怎么理解

一条样本就像一道题：

```text
history          前面聊过什么
previous_state   上一轮已经确认什么
current_user     用户这轮说什么
output           这一轮标准答案是什么
source           这条数据从哪里来
```

### 3.3 面试可以这样说

> 每条样本保留最近 6 轮对话、上一轮累计状态和当前输入，因为指代、补充条件和条件修改都依赖前文。输出统一成累计 belief state、三类 decision、工具调用和缺失字段。

### 3.4 为什么既有 history，又有 previous state

自然说法：

> 历史对话负责保留语言语境，比如“它”“那一家”“换成经济型”；previous state 更像一张已经确认的需求卡片。只给历史，模型每轮都要重新抽取；只给状态，又可能丢掉用户当前的修正语气，所以我把两者一起输入。

### 3.5 belief state 到底是什么

面试时可以说：

> 我把 belief state 理解成截至当前轮已经确认的用户需求。例如用户说“我从故宫出发”，状态里记录出发地为故宫，目的地保持为空，等待用户补充。

### 3.6 数据量怎么说

> 原始候选轮次很多，训练候选大约 4.2 万条。我最终固定了 1,968 条训练、440 条验证和 440 条测试样本，另外保留 80 条 challenge 难例。训练集会照顾不同工具和动作，验证、测试则尽量保留自然分布。

需要记住：

```text
train / validation / test = 1,968 / 440 / 440
challenge = 80
```

### 3.7 为什么训练集要照顾不同类别

> 自然数据里不同动作数量差别很大，如果完全按原始比例训练，模型可能集中学习样本最多的几类。所以训练集保证查询、追问和结束等行为都有足够样本；测试集保留自然分布，用来反映实际数据上的整体表现。

### 3.8 缺参样本怎么说才真实

> CrossWOZ 里的路线请求很多已经包含完整起点和终点，缺参场景数量有限。所以我从同一个数据划分里的真实地点值出发，删除一个必填字段，构造明确标记的缺参样本。比如保留“从故宫出发”，删掉目的地，标准答案就是先追问。来源和构造方式都写进了 manifest，并作为受控消融样本单独记录。

### 3.9 如果面试官问“这不就是你造数据抬分吗”

> 这类样本属于受控构造，作用是单独验证缺参安全行为，数量、来源和 `derived_from` 都有记录。整体 test 和 challenge 分别报告，最终结论以完整测试集为主，缺参切片用于补充说明安全行为。

### 3.10 数据口径

- 原始训练候选约 4.2 万条，最终训练集为 1,968 条。
- 缺参数据包含明确标记的受控消融样本。
- 80 条 challenge 是项目内难例切片，用于观察特定场景表现。

## 4. Agent Trace 到底怎么讲才不书面

### 4.1 自己先这样理解

Agent Trace 就是一份标准化样本档案。它把：

```text
模型看到的上下文
当前允许的工具
模型标准答案
策略标准结果
样本来源
```

放在一起。

### 4.2 面试可以这样说

> 我一开始可以直接从 JSONL 拼 Prompt，但这样训练、评测和 Demo 很容易各自维护一套字段和工具定义。后来我加了一层统一 Trace，把上下文、工具 Schema、模型目标、预期 Policy 结果和来源放在同一条记录里。训练时再从 Trace 渲染 Prompt 和目标 JSON，评测时也能追到每条样本来自哪里。

### 4.3 model target 和 policy target 怎么区分

> model target 是模型这一轮应该建议什么，比如 `ask_user`；policy target 是代码收到这个建议以后应该怎么处理，比如 `needs_input`。一个是模型答案，一个是系统动作，这两个我刻意分开。

### 4.4 工具返回覆盖到哪里

> CrossWOZ 提供多轮对话、用户状态和系统查询标注，工具返回部分为空。因此训练 Trace 记录当前轮的模型目标和预期 Policy 结果，训练任务覆盖调用、追问和结束三类决策。运行阶段再由代码执行符合条件的只读工具。这套口径与源数据证据保持一致。

### 4.5 多轮能力具体指什么

> 输入包含多轮历史和累计状态，每个当前用户轮生成一次工具决策。当前训练范围覆盖“多轮上下文下的一次决策”；工具执行后回填结果、继续规划下一步的循环属于后续扩展方向。

### 4.6 准确表述

> 我训练了多轮上下文下的单步工具决策，并在运行时实现受控执行。Trace 保留模型目标、预期 Policy 结果和样本来源，方便训练、评测和审计共用。

## 5. Prompt 是怎么组织的

### 5.1 面试可以这样说

> 每次输入由四部分组成：固定任务说明、可用工具、上一轮累计状态，以及最近对话加当前用户消息。这样模型既知道协议和工具范围，也能利用自然语言历史和结构化状态。

### 5.2 Base 实验说明了什么

> 我先用同一套 Prompt 跑了 Base。它经常输出解释、Markdown、字段缺失或者错误决策，说明这套 Prompt 下的 1B 基座稳定性较弱。后面的 QLoRA 实验保持 Prompt、数据和解码方式一致，使指标变化主要反映后训练效果。

### 5.3 如果问“Prompt Engineering 多调几次不行吗”

> Prompt 仍有继续优化空间。这个实验先固定 Prompt，用 Base 对照衡量任务后训练带来的稳定增益，因此结论对应当前任务、数据和解码设置。Prompt 优化可以作为另一条独立实验线。

## 6. QLoRA 怎么讲得像自己真的训练过

### 6.1 先说为什么用

> 我的显卡是 6GB，全量训练 1B 模型需要同时容纳权重、梯度、优化器状态和激活，显存成本较高。所以我把基座按 4bit 加载并冻结，只训练 LoRA Adapter。

### 6.2 面试完整说法

> 训练用的是 Gemma 3-1B instruction 版本，基座按 4bit NF4 加载，计算用 FP16。LoRA 用 r16、alpha32、dropout 0.05，挂在 Attention 的 q/k/v/o 和 FFN 的 gate/up/down 层。最终只更新约 1.29% 参数，训练 1 个 epoch，micro batch 是 1，通过梯度累积 8 得到有效 batch 约 8。

### 6.3 Label mask 怎么自然说

> 输入里同时包含 Prompt 和目标 JSON。Prompt 完整参与前向计算，为模型提供历史、状态和工具信息；它对应 token 的 label 设成 `-100`，因此 loss 只统计目标 JSON 部分。可以把它理解成“题目负责提供条件，评分只看答案”。

### 6.4 为什么只有 1 epoch

> 1 个 epoch 后验证 loss 和独立 test 指标已经明显改善。继续增加 epoch 可能带来额外收益，也可能开始过拟合训练格式。因此后续会把 epoch 当成实验变量，以 validation 和 test 的保护指标决定训练长度。

### 6.5 真实训练结果怎么说

> 正式训练用了 1,968 条样本，大约 3 小时 17 分钟。训练 loss 大约 0.129，验证 loss 大约 0.036。最终结论以独立 test 上的格式、状态、决策、工具和参数指标为主，loss 用来观察训练过程。

### 6.6 4bit 具体用在哪里

> 4bit 主要用于冻结基座的量化存储和加载；计算 dtype 是 FP16；参数更新发生在 LoRA Adapter。这三个概念分别对应存储、计算和训练对象。

### 6.7 如果问“LoRA 到底训练了什么”

> 原始大矩阵保持冻结，LoRA 在目标线性层旁边学习一个低秩增量。推理时原始权重输出与任务增量相加，所以 Adapter 比完整模型小很多。

### 6.8 训练口径

> 训练时以 4bit NF4 加载冻结基座，计算使用 FP16，更新对象是 LoRA Adapter，约占总参数的 1.29%。最终能力由独立测试集上的任务指标衡量。

## 7. 模型最终输出什么

模型必须生成：

```json
{
  "belief_state": [],
  "decision": "call_tool",
  "tool_call": null,
  "missing_slots": []
}
```

### 7.1 面试可以这样解释四个字段

> `belief_state` 是到当前为止已经确认的用户需求；`decision` 决定这一轮调用、追问还是不调用；`tool_call` 在调用时保存工具名和参数；`missing_slots` 则说明追问时具体缺什么。

### 7.2 三种 decision 怎么说

> 信息完整并且需要外部查询时是 `call_tool`；需要工具但缺关键参数时是 `ask_user`；感谢、确认或不需要外部信息时是 `no_tool`。

### 7.3 为什么累计状态难

> 模型每轮输出完整累计状态。这样运行时和评测比较直接；随着状态变长，任何槽位遗漏或冗余都会影响严格结果，这也是 JGA 明显低于 Slot F1 的原因。

## 8. 模型输出怎样进入执行系统

### 8.1 先讲真实风险

> 模型生成的是概率文本，系统先把它视为一条待验证的工具建议。常见风险包括字段冗余、字段缺失、未知工具和提示注入，因此真实执行器前面需要独立的校验与授权层。

### 8.2 Contract 怎么说

> 我先做一层输出 Contract，检查原始文本能否解析成 JSON、字段和类型是否合法、decision 和 tool call 是否自洽、工具是否注册，以及参数结构是否含有未知字段。比如模型生成 `run_shell`，注册表查找失败后，这条建议会在 Contract 层被拒绝。

Contract 的职责范围可以这样说：

> 它保证模型建议满足系统接收的结构和协议；随后由 Policy 结合必填参数和风险等级决定执行方式。

### 8.3 Strict JSON 和 Schema 合法怎么说

> 我把格式分成两层。Strict JSON 要求原始输出本身就是一个 JSON 对象；Schema 合法允许先从 Markdown 或解释里抽取 JSON，再检查结构。报告会分别保留两项结果，明确区分原始格式能力和容错解析后的协议合法性。

### 8.4 如果问“为什么不用正则修一下就行”

> 正则适合修复部分格式问题；工具选择、状态遗漏和参数语义则需要对应的评测与校验。我会保留容错解析，同时单独报告 strict JSON，让后处理能力与模型原始能力各自有清晰指标。

## 9. Tool Registry 怎么讲

### 9.1 五个工具

```text
query_attraction_db   景点查询
query_hotel_db        酒店查询
query_restaurant_db   餐馆查询
query_metro_route     地铁路线
request_taxi          打车请求
```

### 9.2 面试可以这样说

> 我把工具名、描述、参数 Schema、必填字段和风险等级集中在一个 Registry 里。Prompt 展示什么工具、Contract 校验什么参数、Policy 判断什么风险，都从同一份注册表读取，避免训练、评测和运行时各维护一套定义。

### 9.3 为什么风险由代码维护

> 风险等级属于系统权限配置，由代码侧 Registry 统一维护。这样即使模型出现幻觉或受到 Prompt Injection，`request_taxi` 的副作用等级仍保持固定，模型只能提出调用建议，授权规则始终由系统掌握。

### 9.4 选对工具后还检查什么

> 选对工具说明语义路由正确。执行阶段还要检查参数完整性、工具风险等级和人工确认要求。模型负责理解需求，Policy 负责授予权限。

## 10. Policy Engine 怎么讲

### 10.1 自己先记四种结果

```text
no_tool               不调用
needs_input            等用户补充
auto_execute           自动执行只读工具
pending_confirmation   等人工确认副作用操作
```

### 10.2 面试可以这样说

> Contract 通过以后，我再用确定性 Policy 做授权。模型给出 `no_tool` 时结束当前轮；给出缺参结果时继续追问；只读工具在参数完整时自动执行；像打车这样的副作用工具进入人工确认。

### 10.3 缺参案例怎么讲

> 用户说“我从故宫出发，帮我叫车”，模型理想输出是 `ask_user`。即使模型误输出 `call_tool`，Policy 仍会检查出发地和目的地，发现目的地缺失后转成 `needs_input`，工具阶段随即跳过。

### 10.4 Prompt 与 Policy 各负责什么

> Prompt 用来引导模型生成符合任务要求的建议，Policy 用确定性分支落实权限边界。即使模型输出发生偏差，代码仍会根据参数和风险等级给出稳定的执行结果。

## 11. Runtime 和本地工具怎么讲

### 11.1 面试可以这样说

> Runtime 负责把 Contract、Policy 和工具执行串起来，并记录每个阶段的事件。只有 Policy 返回 `auto_execute` 时才会调用本地工具，其他情况都会记录跳过原因。这样出现问题时，我能区分是模型输出错、协议没通过、策略拦截，还是工具本身失败。

### 11.2 为什么使用 SQLite

> 本地工具后端用了 SQLite 和裁剪后的 CrossWOZ 参考数据，让 Demo 和测试可以离线复现。这个模块为工具执行提供稳定环境，项目重点则是工具建议如何经过校验、授权和事件记录进入受控执行链路。

### 11.3 三条路径要会自然讲

#### 只读查询

> 比如用户要找经济型酒店，模型输出 `query_hotel_db` 和约束。Contract 通过、Policy 判断它是只读工具以后，Runtime 才执行 SQLite 查询并返回结果。

#### 缺参追问

> 用户只说从故宫出发，目的地为空，Policy 返回 `needs_input`，工具阶段直接跳过。

#### 副作用工具

> 用户给了完整起点和终点并请求打车，模型的调用结构通过校验后，Registry 识别到打车的副作用等级，Policy 返回 `pending_confirmation`，流程停在人工确认环节。

### 11.4 打车路径覆盖到哪里

> 打车工具用于模拟副作用授权路径，验证内容包括参数检查、风险识别和人工确认。当前 Demo 的终点是 `pending_confirmation`，真实派车接口接入属于后续工程阶段。

## 12. 评测怎么讲才不像念指标表

### 12.1 先说为什么这样评

> 我把评测拆成格式、状态、决策、工具、参数和安全几层，因为这些能力会出现不同的错误组合。challenge 切片再单独观察指代、修正和长状态等难例。

### 12.2 Base 和 QLoRA 为什么能公平比较

> 两边使用同一个 Gemma 3-1B、同一份 test、同一 Prompt、同一 4bit 精度和同一贪心解码，实验变量是 Adapter 的加载状态。这样指标变化更容易归因于后训练。

### 12.3 为什么用贪心解码

> 这个任务重点考察协议稳定性。贪心解码每一步选择最高分 token，相同输入更容易复现，也让 Base 和 QLoRA 的对照保持固定。随机采样更适合需要文本多样性的场景。

### 12.4 主结果自然说法

> 在 440 条固定测试集上，QLoRA 把 strict JSON 从 0% 提升到 96.36%，状态 Slot F1 从 1.71% 提升到 89.17%，三类决策准确率从 2.50% 提升到 91.82%，工具选择从 1.14% 提升到 86.93%。这些结果表明模型学会了协议、状态和路由。参数完全匹配为 31.82%，参数精确生成是当前最明显的改进方向。

### 12.5 数字分两层表达

开场只报三个：

```text
strict JSON 96.36%
decision 91.82%
tool 86.93%
```

面试官追问状态和参数时，再补：

```text
state Slot F1 89.17%
state JGA 46.59%
argument Slot F1 68.63%
argument exact 31.82%
```

### 12.6 JGA 和 Slot F1 怎么自然解释

> Slot F1 看状态里有多少单独字段预测正确；JGA 要求整条累计状态完全一致，任何遗漏或冗余都会影响结果。我的样本状态比较长，所以 Slot F1 是 89.17%，JGA 是 46.59%。这说明局部抽取能力较强，长状态完全一致仍有提升空间。

### 12.7 Tool Accuracy 和参数指标怎么区分

> 工具准确率衡量工具名选择；参数 Slot F1 衡量局部参数；参数 Exact 要求整个参数对象完全一致。因此 86.93% 说明路由能力较强，31.82% 的参数 Exact 则反映了完整调用结构的严格表现。

### 12.8 Base 误调用率 0% 怎么解释

> Base 的非工具轮误调用率是 0%，同时它的 strict JSON 也是 0%，说明它很少形成有效协议输出。这个指标需要和协议合法率、call-tool recall 一起看，才能判断模型是真的会停止，还是整体输出能力较弱。

### 12.9 Challenge 怎么说

> 我另外保留了 80 条 challenge，包含指代、条件修正、跨领域、长状态、缺参和结束等场景。它是项目内可解释切片，用于补充观察特定难例，报告口径与 BFCL 等公开 Benchmark 分开。状态和 decision 整体保持稳定，参数指标下降，说明参数泛化相对更弱。

### 12.10 指标口径

- 96.36%：strict JSON，衡量原始输出格式。
- 89.17%：状态 Slot F1，衡量槽位级状态质量。
- 68.63%：参数 Slot F1；更严格的参数 Exact 为 31.82%。
- 80 条 challenge：项目内难例切片，用于定向错误分析。

## 13. 失败和不足怎么讲，反而显得更真实

### 13.1 当前三个主要问题

```text
长状态完全匹配困难
参数精确生成较弱
感谢和结束语偶尔仍会误调用
```

### 13.2 面试可以这样说

> 错误分析里比较明显的三类问题是：状态一长就容易漏一个槽位；工具经常选对，但完整参数有时无法完全一致；还有“好的，谢谢”这种结束语，模型偶尔会继续调用。它们分别对应 JGA、参数 Exact 和非工具轮误调用指标。

### 13.3 31.82% 参数 Exact 说明什么

> 这个严格指标说明完整参数结构仍有明显提升空间。结合工具选择 86.93% 和参数 Slot F1 68.63% 可以看出，模型已经获得路由和局部参数能力，主要瓶颈集中在完整结构的一致性。项目同时证明了后训练对状态和路由的增益，也通过严格指标定位了下一步优化方向；运行时还会对参数完整性进行二次检查。

### 13.4 下一步怎么改

> 我会优先做两个方向。第一是增加结束语和确认语的 no-tool hard negatives，同时观察 call-tool recall，让停止判断和调用能力一起改善。第二是研究 schema-guided decoding 和参数规范化，提高参数 Exact。长状态方面可以尝试 delta state 或服务端状态合并，减少每轮重新生成整个累计状态。

### 13.5 怎样证明改进有效

> 每次只改一个变量，保持模型、测试集、Prompt 和解码方式不变。优化误调用时同时观察 call-tool decision；提高参数 Exact 时同步观察工具选择和状态指标。这样可以确认改进来自目标能力提升，并检查其他能力是否保持稳定。

## 18. 三分钟完整项目介绍

> 这个项目解决的是 Agent 里靠近模型的一层：模型怎样在多轮对话里维护累计状态，并判断当前应该调用工具、继续追问还是结束当前轮。除了生成工具名，我还重点处理前文条件保留、缺参追问和结束语停止三类问题。
>
> 数据来自 CrossWOZ。我保留最近 6 轮对话、上一轮累计状态和当前用户输入，把输出统一成 belief state、decision、tool call 和 missing slots。最终是 1,968 条训练、440 条验证和 440 条测试，另有 80 条 challenge。自然路线数据中的缺参反例较少，所以我做了显式标记的单槽位消融，比如删除目的地，专门测试模型能否停下来追问。
>
> 模型用 Gemma 3-1B，基座 4bit NF4 加载并冻结，LoRA 用 r16，挂在 Attention 和 FFN 的主要投影层，只训练约 1.29% 参数。训练时 Prompt 仍然输入模型，但 label 设成 `-100`，所以 loss 只覆盖目标 JSON。正式训练 1 epoch，大约 3 小时 17 分。
>
> 模型输出以后先进入受控执行链。我用 Contract 检查 JSON、字段、类型、决策不变量和工具白名单；Registry 统一保存五个工具的 Schema、必填参数和风险；Policy 再决定自动执行、继续追问、人工确认或结束。酒店、景点等只读查询可以进入本地 SQLite，打车在参数完整时进入等待确认状态。
>
> 评测时 Base 和 QLoRA 使用相同数据、Prompt、4bit 精度和贪心解码。QLoRA test 的 strict JSON 是 96.36%，状态 Slot F1 89.17%，decision 91.82%，工具选择 86.93%。参数完全匹配为 31.82%，非工具目标轮误调用率为 11.36%。因此我的结论是模型已经形成较强的状态和路由能力，参数精确生成和停止判断是下一阶段重点。

## 19. 高频追问口语答案

### 19.1 “为什么只看最近 6 轮？”

> 这是上下文覆盖、输入长度和噪声之间的工程折中。Gemma 的理论上下文长度更大；这里选择最近 6 轮，并额外输入上一轮累计状态来保留更早信息。长状态指标仍然下降，说明这套折中还有优化空间。

### 19.2 “为什么选择输出累计状态？”

> 累计状态便于运行时直接做全量校验，也能直接计算 JGA；相应代价是状态越长，完全一致的难度越高。下一步可以对比 delta state 加服务端合并，观察它对长状态和生成长度的改善。

### 19.3 “为什么不把 decision 做成分类器？”

> 分类器是一个合理的对照方案。当前任务同时生成三类 decision、累计状态、工具和嵌套参数，所以我先统一成生成协议。以后可以把 decision 拆成分类头进行消融，观察它对 no-tool 误调用的影响。

### 19.4 “为什么工具参数和 belief state 不完全一样？”

> belief state 保存的是所有累计用户目标，工具参数是当前一次调用需要的投影。状态里可能有多个领域和历史条件，而某个查询只需要当前工具相关的 constraints 和 requested fields。

### 19.5 “Schema 合法以后还经过哪些步骤？”

> Schema 合法表示结构和字段关系通过检查。随后 Policy 继续检查必填参数和风险等级；副作用工具会进入人工确认，只读工具在参数完整时才进入自动执行。

### 19.6 “你的指标怎样复现？”

> 仓库保留固定数据、逐样本原始生成、聚合脚本和自动报告。可以从单条 prediction 对到 target，再运行 analyze 和 benchmark 重新生成汇总。训练参数也保存在 Adapter 的 training metrics 中。

### 19.7 “为什么验证 loss 比训练 loss 低？”

> 训练 loss 是训练过程中的平均值，包含模型尚在收敛时的早期 step，并且训练时有 dropout；验证是在 epoch 结束后用当前模型、冻结参数进行计算。两者的统计时点和运行模式不同，最终仍以独立任务指标判断效果。

### 19.8 “模型输出 Markdown 怎么办？”

> 评测先记录原始输出是否 strict JSON，再允许容错提取 JSON 做 Schema 检查。报告分别展示原始格式能力和容错后的结构合法性。进一步可以加入 constrained decoding，提高原始输出的协议稳定性。

### 19.9 “为什么 KV Cache 和项目有关？”

> 模型生成 JSON 是自回归过程，KV Cache 保存前文已经计算的 K/V，生成新 token 时直接复用。它节省前缀的重复计算，模型参数量保持不变，缓存本身还会占用显存。

### 19.10 “项目里的可靠性包含什么？”

> 我同时关注模型答对多少、结束场景能否停止、参数缺失时能否追问、副作用工具能否被拦截，以及失败能否按场景定位。可靠性由模型指标、代码权限边界和可审计执行共同组成。

### 19.11 “如果模型输出未知参数会怎样？”

> Registry 的参数 Schema 将未知顶层参数视为协议错误，Contract 会直接拒绝。对于实体查询内部的约束，工具端也会显式返回未知字段问题，便于定位错误。

### 19.12 “当前数据和线上应用之间是什么关系？”

> 这是一个可复现实验项目，使用公开 CrossWOZ 和本地 SQLite，用于验证方法和代码边界。真实上线还需要补充业务流量数据、shadow evaluation、线上监控和权限审计。

### 19.13 “你的项目最有价值的设计是什么？”

> 我认为最有价值的设计是把模型提议和执行授权分开。即使模型偶尔生成错，Contract 和 Policy 仍能拒绝未知工具、降级缺参调用并拦住副作用操作。这让模型能力和系统安全可以独立评估。

### 19.14 “如果只允许你改一个地方，你改什么？”

> 我会先改结束语误调用，因为它直接影响停止判断。我会增加 no-tool hard negatives，并同时观察 call-tool recall，让停止能力和正常调用能力一起保持稳定。
