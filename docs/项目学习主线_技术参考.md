## 0. 先只记住三句话

第一句：

> 用户说话以后，Gemma 负责理解用户当前想做什么，并提出一个结构化工具决策。

第二句：

> Gemma 只能提出建议，真正能否执行由代码检查；模型没有给自己授权的能力。

第三句：

> 项目用固定测试集比较 Base 和 QLoRA，证明微调让格式、状态、决策和工具选择明显提升，同时保留参数生成和误调用等失败。

整套项目就是：

```text
用户多轮对话
   ↓
Gemma 输出 JSON 建议
   ↓
代码检查和授权
   ↓
查询工具 / 继续追问 / 人工确认 / 不调用
   ↓
评测到底做对了多少
```

第一遍学习时，任何知识都要放回这五步中。放不回去的细节先不学。

## 1. 用一条案例贯穿整个项目

我们只看这一句话：

```text
用户：我从故宫出发，帮我叫辆出租车。
```

这句话包含：

- 用户想使用出租车能力；
- 出发地是故宫；
- 目的地没有提供。

所以正确行为应该是：

```text
不要猜目的地
不要调用打车工具
先追问用户目的地
```

模型的标准答案是：

```json
{
  "belief_state": [
    {
      "goal_id": 1,
      "domain": "出租",
      "constraints": {"出发地": "故宫"},
      "requested_fields": []
    }
  ],
  "decision": "ask_user",
  "tool_call": null,
  "missing_slots": ["目的地"]
}
```

先不要记字段定义，只回答：

1. 用户已经说了什么？——出发地是故宫；
2. 用户没说什么？——目的地；
3. 当前能执行吗？——不能；
4. 系统下一步做什么？——追问目的地。

如果这四个问题能回答，已经理解了项目最核心的安全行为。

## 2. 第一站：数据告诉模型“什么是正确答案”

### 2.1 原始数据是什么

项目使用 CrossWOZ 中文多领域任务型对话，包含：

- 用户和助手的多轮对话；
- 景点、酒店、餐馆、地铁和出租等领域；
- 用户已经表达的结构化状态；
- 系统后续查询行为。

模型不能只看最后一句，因为用户经常这样说：

```text
用户：我想去故宫。
助手：好的。
用户：它附近有什么酒店？
助手：需要什么类型？
用户：经济型，评分 4.5 以上。
```

最后一句没有出现“故宫”和“酒店”，但它们仍然是当前目标的一部分。

### 2.2 项目怎样保存一条样本

一条样本可以先理解成：

```text
以前聊了什么       history
上一轮已经确认什么 previous_state
用户这轮说什么     current_user
正确答案是什么     output
数据从哪里来       source
```

实际文件：[test.jsonl](../data/tool_use/test.jsonl)

第一遍只看一条，千万不要连续读 440 条。

### 2.3 什么是 belief state

`belief_state` 是“截至当前轮，用户已经明确表达的累计目标”。

它不是模型的内心想法，也不是聊天记录复制，而是一份结构化任务笔记：

```json
{
  "domain": "出租",
  "constraints": {"出发地": "故宫"}
}
```

你可以把它想成客服系统右侧的用户需求卡片。

### 2.4 为什么要补缺参样本

原始数据中很多路线请求已经同时给出起点和终点。只用这些样本，模型可能只会“有参数就调用”，却学不会“参数不足时停止”。

因此项目把完整句子：

```text
我从故宫出发，叫车去颐和园。
```

受控地删除目的地：

```text
我从故宫出发，帮我叫辆出租车。
```

并把来源明确标成 `controlled_required_slot_ablation`。这不是冒充自然数据，而是专门验证安全能力的受控测试。

### 2.5 这一站只需会说

> 项目把 CrossWOZ 多轮对话转换成包含历史、上一轮状态、当前输入和标准工具决策的样本；另外显式构造缺参样本，让模型学习信息不足时必须追问。

对应代码以后再看：[build_tool_use_dataset.py](../scripts/build_tool_use_dataset.py)。

## 3. 第二站：把样本整理成 Agent Trace

### 3.1 为什么不直接拼 Prompt

如果训练脚本、评测脚本和 Demo 各自理解一套数据，容易出现：

- 训练看到的工具列表与运行时不一致；
- 数据来源丢失；
- 模型目标和策略目标混在一起；
- 修改 Prompt 后不知道原始标签代表什么。

所以项目先建立一份统一记录，叫 Canonical Agent Trace。

### 3.2 Trace 只回答五个问题

```text
1. 上下文是什么？       context
2. 系统允许哪些工具？   tools
3. 模型应该输出什么？   model_target / expected
4. 策略应该怎么处理？   policy_target
5. 样本从哪里来？       provenance
```

对我们的案例：

```text
context：用户从故宫出发，但没有目的地
model target：ask_user
policy target：needs_input
provenance：受控缺参样本
```

### 3.3 为什么没有伪造工具返回

源数据没有项目五个本地工具的真实执行结果，所以训练 Trace 只记录模型目标和预期策略结果，不伪造 `tool_response`。

这意味着项目已完成“单轮决策 + 受控执行”，但不能夸成“训练了完整多步工具轨迹”。

### 3.4 这一站只需会说

> Agent Trace 是统一中间表示，把对话上下文、工具、模型标准答案、策略标准结果和样本来源放在一起，供训练、审计和评测共同使用。

对应代码：[traces.py](../src/gemma_eval/traces.py)。

## 4. 第三站：把 Trace 变成模型真正看到的 Prompt

模型最终看到的是一段文字，包含四部分：

```text
任务说明
+ 可用工具
+ 上一轮状态
+ 最近对话和当前输入
```

对我们的案例，意思大致是：

```text
你是工具决策模块，只输出 JSON。

可用工具包括景点、酒店、餐馆、地铁和打车。

上一轮状态为空。

用户：我从故宫出发，帮我叫辆出租车。

JSON：
```

模型训练目标则是前面看到的标准 JSON。

### 为什么既要历史，又要上一轮状态

- 历史保留“它、那家、换成经济型”等自然语言语境；
- 上一轮状态提供已经确认的结构化任务笔记；
- 两者结合比每轮重新从所有聊天中抽取更稳定。

### 这一站只需会说

> Prompt 同时给模型任务协议、工具说明、上一轮累计状态和最近对话，使它能根据多轮上下文生成本轮结构化决策。

对应代码：[tool_use_data.py](../src/gemma_eval/tool_use_data.py)。

## 5. 第四站：QLoRA 教 Gemma 稳定输出这个协议

### 5.1 Base 模型的问题

未经任务适配的 Gemma 可能输出：

```text
好的，请告诉我您的目的地。
```

也可能输出：

````text
```json
{"decision":"ask_user"}
```
````

或者字段缺失、状态错误、工具名错误。

但本项目要求稳定生成固定四字段 JSON，不能只靠自然语言回答。

### 5.2 QLoRA 用最简单的话理解

```text
冻结原来的 Gemma 3-1B
+ 以 4bit 方式加载，减少显存
+ 在部分线性层旁增加小型 LoRA 参数
+ 只训练这些新增参数
```

可以类比：不重写整本教材，而是给教材增加一组专门针对 Tool-Use 的可训练批注。

真实设置只需要先记四个：

```text
Gemma 3-1B
4bit NF4
LoRA r=16
训练 1 epoch
```

### 5.3 模型训练时看什么、学什么

训练输入：

```text
Prompt tokens + 正确 JSON tokens
```

计算 loss 时：

```text
Prompt 位置：不计分
答案位置：计分
```

这叫 label mask。Prompt 并没有被删除，模型仍然必须读取它；只是训练不要求模型复述题目，只对答案评分。

### 5.4 这一站只需会说

> 项目用 4bit QLoRA 冻结 Gemma 基座，只训练少量 Adapter 参数，并只对目标 JSON 计算 loss，让模型适应多轮状态和固定工具决策协议。

对应代码：[train_tool_use_qlora.py](../scripts/train_tool_use_qlora.py)。

## 6. 第五站：模型输出四个字段

模型输出：

```json
{
  "belief_state": [],
  "decision": "ask_user",
  "tool_call": null,
  "missing_slots": ["目的地"]
}
```

四个字段只这样理解：

| 字段 | 人话 |
| --- | --- |
| `belief_state` | 用户目前已经明确说了什么 |
| `decision` | 现在调用、追问还是停止 |
| `tool_call` | 如果调用，使用什么工具和参数 |
| `missing_slots` | 如果追问，缺少什么信息 |

三种 decision：

```text
call_tool  信息完整，需要外部工具
ask_user   需要工具，但缺少关键参数
no_tool    当前不需要外部工具
```

字段关系：

| decision | tool_call | missing_slots |
| --- | --- | --- |
| `call_tool` | 必须有 | 必须为空 |
| `ask_user` | 必须为 null | 至少一个 |
| `no_tool` | 必须为 null | 必须为空 |

我们的案例应输出 `ask_user`，因为目的地缺失。

## 7. 第六站：Contract 先检查模型有没有胡写

模型输出只是文本，可能出现：

- 不是 JSON；
- 多出解释或 Markdown；
- 字段名错误；
- decision 不存在；
- `ask_user` 却没有缺失字段；
- 使用系统没注册的工具；
- 参数类型错误。

Contract 像进入系统前的安检，负责检查：

```text
JSON 能不能解析
字段是否允许
类型是否正确
decision 是否合法
四个字段之间是否自洽
工具是否注册
参数结构是否正确
```

例如模型输出：

```json
{
  "belief_state": [],
  "decision": "call_tool",
  "tool_call": {"name": "run_shell", "arguments": {}},
  "missing_slots": []
}
```

`run_shell` 不在白名单中，Contract 直接拒绝，不能进入执行层。

### 这一站只需会说

> Contract 不判断回答是否聪明，而是检查模型提议是否满足系统允许的 JSON 结构、字段类型、决策不变量和工具白名单。

对应代码：[contracts.py](../src/gemma_eval/contracts.py)。

## 8. 第七站：Registry 和 Policy 决定能不能执行

### 8.1 Registry 是工具说明书

系统注册五个工具：

| 工具 | 用途 | 风险 |
| --- | --- | --- |
| `query_attraction_db` | 查询景点 | 只读 |
| `query_hotel_db` | 查询酒店 | 只读 |
| `query_restaurant_db` | 查询餐馆 | 只读 |
| `query_metro_route` | 查询地铁 | 只读 |
| `request_taxi` | 请求打车 | 有副作用 |

Registry 保存工具名、参数格式、必填参数和风险等级。

风险必须写在代码里，不能让模型输出。否则模型可以通过生成“这个工具很安全”给自己提权。

对应代码：[tool_registry.py](../src/gemma_eval/tool_registry.py)。

### 8.2 Policy 是授权员

Policy 不重新理解用户语言，它只根据已经通过 Contract 的决策和 Registry 规则授权：

```text
no_tool
→ 不调用

ask_user
→ 继续追问

只读工具 + 参数完整
→ 自动执行

必填参数不完整
→ 继续追问

副作用工具 + 参数完整
→ 等待人工确认
```

我们的案例：

```text
模型：ask_user
Policy：needs_input
工具：不执行
```

即使模型错误输出 `call_tool`，Policy 也会再次检查地铁/打车的出发地和目的地。缺参数时仍然不会执行。

对应代码：[policy.py](../src/gemma_eval/policy.py)。

### 这一站只需会说

> Registry 声明系统有哪些工具、参数和风险；Policy 根据这些代码规则决定自动执行、追问、人工确认或不调用。模型只能建议，不能授权。

## 9. 第八站：Runtime 执行并留下事件记录

Runtime 把前面的模块串起来：

```text
模型输出
  ↓
Contract 检查
  ↓
Policy 授权
  ↓
只有 auto_execute 才调用本地工具
  ↓
记录每一步事件
```

我们的缺参案例会产生：

```text
contract：accepted
policy：needs_input
tool：skipped
```

酒店查询可能产生：

```text
contract：accepted
policy：auto_execute
tool：ok，返回 SQLite 查询结果
```

完整打车请求产生：

```text
contract：accepted
policy：pending_confirmation
tool：skipped
```

Runtime Event Trace 的作用是排错和审计：以后可以看出错误发生在模型、Contract、Policy 还是工具。

对应代码：[runtime.py](../src/gemma_eval/runtime.py) 和 [local_tools.py](../src/gemma_eval/local_tools.py)。

## 10. 第九站：Eval 判断模型到底做对了多少

不能只展示一个成功 Demo，因为挑一条成功案例不能代表模型可靠。

评测流程：

```text
固定测试数据
→ Base 或 QLoRA 生成
→ 保存原始输出
→ 检查格式和 Schema
→ 与标准答案比较
→ 汇总指标和失败样本
```

Base 和 QLoRA 使用相同：

- 测试集；
- Prompt；
- 4bit 精度；
- 贪心解码；
- 最大生成长度；
- 解析和指标代码。

主要区别只有是否加载 Adapter，这样才能把提升归因于后训练。

### 第一遍只看五个指标

| 问题 | 指标 | QLoRA test |
| --- | --- | ---: |
| 能不能输出纯 JSON | strict JSON | 96.36% |
| 状态中的槽位对多少 | state Slot F1 | 89.17% |
| 调用/追问/停止是否正确 | decision accuracy | 91.82% |
| 需要调用时工具选对多少 | tool accuracy | 86.93% |
| 完整参数完全一致多少 | argument exact | 31.82% |

前四项说明模型学到了明显能力；最后一项说明参数精确生成仍然很弱。

另外一个重要问题：无需工具轮仍有 11.36% 被误调用，典型案例是“好的，谢谢”之后模型还继续查询。

### 这一站只需会说

> 项目不只看格式或一个准确率，而是分别评估状态、决策、工具、参数和误调用。QLoRA 提升明显，但参数完全匹配和停止能力仍是主要短板。

对应代码：[evaluate_tool_use.py](../scripts/evaluate_tool_use.py)，结果见 [实验报告](../reports/EXPERIMENT_REPORT.md)。

## 11. 把三条执行路径放在一起

### 路径 A：缺参追问

```text
用户：我从故宫出发，帮我叫车
→ 模型 ask_user
→ Contract 通过
→ Policy needs_input
→ 工具不执行
```

### 路径 B：自动执行只读查询

```text
用户：查询评分 4.5 以上的经济型酒店
→ 模型 call_tool / query_hotel_db
→ Contract 通过
→ Policy auto_execute
→ SQLite 返回酒店结果
```

### 路径 C：副作用工具人工确认

```text
用户：从故宫叫车去颐和园
→ 模型 call_tool / request_taxi
→ Contract 通过
→ Registry 标记 side_effect
→ Policy pending_confirmation
→ 不自动执行
```

如果能不看资料讲清这三条路径，主线已经掌握一半以上。

| 8 | `runtime.py` | 各层怎样串起来 |

第二遍才看：数据构建全部函数、指标聚合、Benchmark、Gemma 内核和所有测试。

## 15. 十道主线验收题

### 1. 这个项目一句话做什么？

用小模型理解多轮状态并提出工具决策，再由确定性代码校验和授权。

### 2. 为什么不能只看当前一句话？

用户的目标、指代和条件修改分散在多轮对话中。

### 3. belief state 是什么？

截至当前轮已经确认的结构化用户目标。

### 4. 为什么要有 ask_user？

缺少必填参数时不能猜测或执行，必须先补充信息。

### 5. QLoRA 教模型什么？

根据多轮上下文稳定生成固定状态和工具决策 JSON。

### 6. Contract 做什么？

检查 JSON、字段、类型、决策关系、工具白名单和参数结构。

### 7. Registry 做什么？

统一声明工具、参数、必填字段、风险和执行信息。

### 8. Policy 做什么？

决定自动执行、继续追问、人工确认或不调用。

### 9. 为什么模型不能自己决定风险？

模型输出不可信；如果风险字段由模型控制，它就可能给自己提权。

### 10. 项目当前最大的短板是什么？

参数完全匹配较低、长状态完全一致困难、结束语存在误调用。

十题能用自己的话回答，第一遍就算过关。

## 16. 30 秒和 3 分钟讲法

### 30 秒

> 我把 CrossWOZ 多轮对话转换成带历史、累计状态和工具决策的 Agent Trace，再用 4bit QLoRA 训练 Gemma 3-1B 输出调用、追问或不调用的结构化 JSON。模型输出不会直接执行，而是经过 Contract、工具注册表和 Policy 校验，只读工具可以自动查询，打车等副作用工具必须人工确认。测试集上决策准确率达到 91.82%，同时参数精确生成和结束语误调用仍是主要短板。

### 3 分钟只按六段

```text
1. 问题：多轮状态和工具调用不稳定
2. 数据：CrossWOZ + 状态 + 缺参样本
3. 训练：Gemma 3-1B + 4bit QLoRA
4. 输出：四字段 JSON 和三种 decision
5. 执行：Contract + Registry + Policy + Runtime
6. 证据：Base 对照、主指标、真实失败
```

不要在前三十秒就开始讲 NF4、JGA、RoPE 或具体类名。先让面试官知道项目解决什么问题。
